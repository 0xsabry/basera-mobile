## 1. Current architecture assessment (verified by inspection)

- **Stack:** Expo SDK 58 / RN 0.88 / TypeScript / expo-router. Package
  `me.auramarketing.basera`, EAS project `@0xsabry/basera`
  (`f402737d-1b54-441d-8738-99ce8e9009e9`), profiles: `development`
  (dev client) and `preview` (standalone internal APK, FINISHED + verified).
- **The app is 100% offline.** A full scan of `src/` finds zero `fetch`/HTTP
  calls. All AI is on-device: YOLO11n (TFLite), ML Kit Latin OCR, PP-OCR
  Arabic OCR, expo-speech TTS, expo-speech-recognition commands.
- **There is NO BASERA backend.** No server code, no API client, no account
  system, no database, no push infrastructure exists in this project today.
  (The user's unrelated e-commerce systems on other infrastructure are not
  a BASERA backend and are not proposed as one — see §4.1.)
- **Not installed:** `expo-updates`, `expo-location`, `expo-notifications`,
  `expo-task-manager`, maps, any auth/backend SDK. The built preview APK was
  inspected: it contains **no expo-updates native code** (see §8).
- **Reusable architecture:** clean service seams already exist —
  `ImageSource` (gallery/sample/phone-camera-test/future-glasses),
  `ObjectDetector`, `TextRecognizer`, `SpeechService` (with the
  repeatable/announcement split), `VoiceCommandService`,
  `ObstacleAwareness` (position + heuristic proximity category),
  `HistoryStore` (AsyncStorage), `SettingsContext`, full AR/EN i18n with RTL.
- **Identity/privacy today:** no user accounts; history lives only on the
  device. Guardian features change this fundamentally — they introduce
  accounts, a server, and sensitive location data, and must be designed as
  such (§5).

## 4. Data model and API design

### 4.1 Backend choice — DECISION REQUIRED before Phase 1
Guardian tracking needs a small, always-on, authenticated backend. Options:

- **A. Managed BaaS — Supabase (recommended).** Postgres + Auth (email/phone
  OTP) + Row Level Security + Realtime + Edge Functions + storage, free
  tier is enough for a graduation-project pilot. RLS maps directly onto the
  guardian authorization model (§5). Push via Expo Push Service from an
  Edge Function (or FCM directly).
- **B. Firebase (Auth + Firestore + FCM).** Equally viable; security rules
  instead of RLS; best Android push story. More vendor lock-in, rule
  language is less auditable than SQL RLS.
- **C. Custom backend on the user's own servers.** Full control, but: his
  current hosting is a fragile sandbox VM with frequent platform
  replacements (documented in project history) — **not acceptable for
  location data of a vulnerable user** without moving to a real VPS, and it
  adds auth/security surface we would have to build and audit ourselves.
  Not recommended for V1.1.

This plan is written against **A (Supabase)**; choosing B changes only the
implementation of the same model, not the model.

### 4.2 Data model (relational sketch)
- `users` — id (auth uid), display_name, role flags, created_at.
  The protected user and guardians are both `users`; the *link* carries the
  relationship, not the account type.
- `guardian_links` — id, owner_user_id (the BASERA user), guardian_user_id,
  status (`pending`/`active`/`revoked`), created_at, revoked_at.
  **Unique (owner, guardian).** A guardian sees a user's location **iff** an
  `active` link exists. Revocation is a status flip + immediate RLS effect.
- `pairing_codes` — id, owner_user_id, code_hash (never store the raw code),
  expires_at (≤15 min), used_at, attempts. Single-use.
- `location_points` — id, user_id, lat, lng, accuracy_m, recorded_at
  (device), received_at (server), source (`foreground`/`background`),
  battery_pct (optional, only if the user enables it). Retention (**OWNER DECISION 2026-10-30: 24 hours**, superseding the
  earlier 7-day recommendation): detailed points are auto-deleted after
  **24 hours**; only the latest location is kept, and only while sharing
  is active. Disabling sharing or revoking access stops uploads
  immediately and deletes the user's stored location records server-side.
- `hazard_events` — id, user_id, created_at, hazard_class (taxonomy §6.3),
  risk_level (`low`/`medium`/`high`), confidence, direction,
  proximity_category, source (`phone-yolo`/`glasses-metadata`/`manual-sos`),
  acknowledged_at, guardian_notified_at. Photo evidence is **not** uploaded
  by default (privacy); if ever added it needs explicit per-event consent.
- `push_endpoints` — user_id, platform, endpoint, updated_at. **OWNER
  CORRECTION:** Android app notifications and guardian web notifications
  are SEPARATELY registered endpoints — platform `android-expo` (Expo
  Push token) vs `web-fcm` (FCM Web Push token). Guardian browser
  notifications use **FCM Web Push** (HTTPS PWA + service worker +
  permission flow); Expo Push cannot deliver to ordinary web clients.
  FCM credentials and the Supabase service-role key live only on the
  server (Edge Function secrets).
- `device_settings` (server mirror, optional) — sharing_enabled,
  update_interval_profile. The phone remains the source of truth; the
  server never *enables* sharing — it can only record the user's choice.

### 4.3 API surface (all HTTPS, all authenticated, no public URLs)
- `POST /pairing/request` (guardian scans/enters code) → creates `pending`
  link; owner approves in-app (or auto-approve within code validity —
  decision: **owner approval tap required**; the code alone never grants
  access).
- `POST /locations` (user's app, batched) → append points, update latest.
- `GET /guardians/me/locations` (guardian app/web view) → last-known +
  history window for owners with an `active` link to the caller. Enforced
  by RLS, not by client filtering.
- `POST /hazard-events` → store + trigger guardian push for `high` risk
  (and `medium` if the user configured it).
- `POST /links/{id}/revoke` (either side) → effective immediately.
- Guardian map: a small authenticated page/app screen reading the same API;
  map tiles via OpenStreetMap (no API key, no location leakage to a
  third-party *app* backend beyond tile requests) — **OWNER DECISION:
  the guardian client is a responsive, installable PWA** (service
  worker, manifest), not a basic page or a second native app — or `react-native-maps`
  with Google provider if the team prefers; tiles choice does not affect
  the security model. **Location data itself is only ever served by our
  API to an authenticated, linked guardian. No share-links, no tokens in
  URLs, no public endpoints.**

## 5. Guardian pairing and security model

1. **Opt-in first:** location sharing defaults OFF. Enabling it requires:
   account sign-in → plain-language explanation screen (AR/EN, spoken) →
   foreground permission → (separately, later) background permission with
   its own explanation. Each step is independently revocable.
2. **Pairing:** the BASERA user generates a one-time code (6 digits + QR of
   the same payload) valid ≤15 minutes. The guardian enters/scans it in
   their own signed-in app → link becomes `pending` → the BASERA user sees
   "Guardian X wants to follow your location — Allow / Deny" (spoken +
   large buttons). Only Allow activates. Codes are hashed at rest,
   rate-limited (≤5 attempts), single-use.
3. **Authorization:** database-level RLS: `location_points` selectable only
   by `user_id = auth.uid()` or by a caller with an `active` link as
   guardian. Server-side enforcement; the client is never trusted.
4. **Transport & storage:** TLS everywhere (platform default), tokens in
   `expo-secure-store`, refresh-token rotation, no location data in push
   payloads (push says "New hazard event" / "Location updated"; the
   guardian app fetches details after authenticating).
5. **Revocation:** one tap in Settings → link `revoked` server-side →
   guardian's next read returns nothing; the app also stops uploading
   immediately when sharing is toggled off locally (local kill-switch does
   not depend on the network).
6. **Abuse cases handled by design:** guessing codes (hashing + rate limit
   + expiry + owner approval), stolen guardian phone (guardian can be
   revoked by owner; guardian account has its own auth), curious insider /
   DB leak (no public URLs; raw retention 24 hours (owner decision); audit log of link
   changes kept 90 days).
7. **Honesty constraints:** connection status shown to both sides is
   derived from `received_at` freshness ("updated 3 min ago" / "offline —
   last seen …"), never a fake "live" indicator.

## 6. Glasses-to-phone communication design

### 6.1 What is actually known
Nothing about the glasses hardware: no chipset, radio, camera, or firmware
exists or has been specified (project's standing fact since day one). Any
plan that assumes BLE/Wi-Fi specifics today would be fiction. Therefore:

### 6.2 Interim real path (no glasses required)
Hazard detection ships first on the **phone**: `PhoneCameraTestSource` /
gallery frames → existing YOLO pipeline → risk engine (§6.3) → voice +
vibration + (Phase 3) guardian push. This is fully implementable and
testable in V1.1 and is the reference implementation the glasses must
later feed.

### 6.3 Hazard taxonomy and risk evaluation (grounded in the real model)
The shipped YOLO11n is COCO-80. Relevant classes — and their limits:

| Hazard category | COCO classes | Base risk | Notes |
|---|---|---|---|
| Vehicle in path | car, bus, truck, motorcycle, bicycle, train | high when near+center | Cannot tell moving vs parked; no speed/direction of travel |
| Person proximity | person | medium (context) | A person is usually not a hazard; risk rises only near+center+persistent (possible collision course) — never alert "danger" for a person alone at low proximity |
| Animal | dog, cat, horse, cow, bear, elephant, … | medium | Size/distance unknown beyond proximity category |
| Sharp object | knife, scissors | medium | Only meaningful near; high false-positive rate in kitchens (context problem — documented) |
| Static obstacle | chair, bench, couch, dining table, potted plant, bed | low | Already covered by obstacle awareness; hazard alerts should NOT duplicate routine obstacle descriptions |
| **Not detectable by this model** | stairs, holes/drop-offs, fire/smoke, glass doors, hanging obstacles above camera line, weapons, water/ice | — | **Must be stated in-app and in the thesis**: the system cannot warn about these. Absence of an alert never means "safe". |

Risk engine rules (deterministic, unit-testable, no ML magic):
- Inputs per frame-batch: detections (class, confidence, direction,
  proximity category from bbox geometry).
- Per-class confidence thresholds (vehicles lower threshold, sharps higher).
- **Persistence:** a hazard must appear in ≥2 of 3 consecutive evaluations
  before alerting (kills single-frame false positives).
- **Cooldown:** same class+direction suppressed for 20 s after an alert
  (configurable); escalating proximity (medium→near) breaks cooldown.
- **Risk levels:** low = spoken info only if user enabled verbose mode;
  medium = short voice alert + single vibration; high = voice alert
  (announcement channel + becomes the Repeat target) + strong vibration
  pattern + hazard event recorded + guardian push (if enabled).
- **Escalation:** 3 high alerts within 5 min with no user acknowledgment
  (voice command "I'm okay" / button) → guardian push marked urgent.
  A manual SOS (voice command + big button) always creates a high event
  with current location attached (if sharing on).
- **False-positive budget:** alert fatigue destroys trust in an
  accessibility product; thresholds ship conservative (fewer, surer
  alerts) and are tuned only from the controlled-test data (§6.5).

### 6.4 Phone-side alert delivery
Voice via `SpeechService` (Arabic first), vibration via `expo-haptics`/
RN Vibration with distinct patterns per level, on-screen high-contrast
banner for low-vision users. Alerts never trigger an OTA reload (§8.4) and
never block an in-progress TTS message — they queue behind it (except SOS).

### 6.5 Testing plan for hazard detection (no accuracy claims without it)
- Controlled staged scenarios (empty hall → street edge): vehicles at
  3 distances × 3 directions, person approach, dog, chair obstacle —
  each ≥20 trials, logged detections vs ground truth.
- Metrics per category: precision, recall, false alerts/hour in a
  30-min "ordinary walk" negative control, alert latency (frame→voice).
- Acceptance gates are set from pilot data, not promised in advance.
  Until then, all user-facing copy calls this "experimental assistance",
  never a safety guarantee.

### 6.6 Future glasses contract (design only — no protocol invented)
When hardware exists, it must satisfy an interface, not a wish:
- Transport candidates ranked: **BLE GATT** (metadata-first, low power —
  recommended if the glasses can run detection or send small frames),
  Wi-Fi Direct/local hotspot (needed if raw frames stream to the phone),
  USB-C tether (dev/debug). Final choice requires the hardware's radio +
  power budget — a decision gate, not a default.
- Two integration shapes, both already supported by our seams:
  (a) glasses send **detection metadata** `{timestamp, class, confidence,
  bbox?}` → phone risk engine (`HazardEventSource` interface, sibling of
  `ImageSource`); (b) glasses send **frames** → existing
  `SmartGlassesCameraSource` → same YOLO pipeline.
- The phone remains the alert authority in both shapes (TTS, vibration,
  guardian push live here). Versioned message schema + capability
  handshake fields are specified when the hardware team freezes v0 specs.

## 8. OTA updates — EAS Update assessment and design

### 8.1 Compatibility assessment for the ALREADY-BUILT preview APK
**Verdict: the current preview APK (9b80e739) can never receive OTA
updates.** Verified by inspecting the artifact: it contains no
`expo-updates` native module, and the project has no `updates` config, no
`runtimeVersion`, and no channel mapping. OTA capability is a *native*
property — it must be present in the APK. **One more APK build is
mandatory** to enable OTA; after that build, JS/assets updates flow
without reinstallation. The development build has the same limitation.

### 8.2 Target configuration (Phase 0)
- Install `expo-updates` (SDK 58 version) + `expo-updates` config plugin.
- `app.json`: `updates.url = "https://u.expo.dev/f402737d-1b54-441d-8738-99ce8e9009e9"`,
  `updates.enabled: true`, `updates.checkAutomatically: "ON_LOAD"`,
  `updates.fallbackToCacheTimeout: 0` (never block an accessibility app's
  startup on the network).
- `runtimeVersion`: `{ "policy": "appVersion" }` — runtime tracks the
  app version string. Rule: **any native change bumps `version`**
  (1.1.0 → 1.2.0 …) which automatically makes old runtimes ineligible for
  newer JS. (Fingerprint policy was rejected: it re-hashes on harmless
  config diffs and is harder for the team to reason about; appVersion is
  explicit and matches our release discipline.)
- Channels in `eas.json`: `preview` profile gets `"channel": "preview"`;
  a new `production` profile (created when needed, **not built now**) gets
  `"channel": "production"`. The existing `development` profile stays
  untouched (dev client ignores OTA).
- Version bump for the OTA-foundation APK: `1.0.0 → 1.1.0` (it is also the
  V1.1 feature APK — one new build carries updates + location + notifications
  natives, avoiding two disruptive reinstalls).

### 8.3 In-app update experience
New **Update Status** section (Settings + a dedicated screen):
shows current runtime version, channel, embedded update ID, last check
time, and states: up-to-date / checking / downloading / ready (applies on
next restart) / error with retry. Flow: `checkForUpdateAsync()` on app
start (background, non-blocking) → `fetchUpdateAsync()` → update is
**staged, never auto-reloaded mid-session** → applied on natural restart,
or via an explicit spoken-confirmed "Restart to apply" button.
Release notes do NOT come from the `eas update --message` text (**OWNER
CORRECTION:** that text is not reliably available to the app). They live
in a separate versioned in-bundle source, `src/update/releaseNotes.ts`,
updated in the same commit as each change and displayed on the update
screen.

### 8.4 Safety rules
- **Never** reload during: an active hazard alert, TTS playback, voice
  recognition, or an OCR/detection run (the update manager checks an
  "accessibility operation in progress" flag owned by the app state).
- Failed update download = stay on the embedded bundle, silently retry
  next launch; a corrupt update is rejected by EAS Update's own signature
  checks. Rollback: `eas update:rollback`; promotion of the exact
  tested update: `eas update:republish --destination-channel production`
  (**OWNER CORRECTION** — see §8.5). The embedded-in-APK bundle is always
  the last-resort fallback.
- **Code signing is NOT enabled by default and is NOT configured here**
  (**OWNER CORRECTION**): EAS Update code signing requires subscription
  eligibility + explicit certificate setup. Verify eligibility on the
  Expo account and configure it explicitly before claiming signed
  updates. No custom update server is used either way.

### 8.5 Publishing procedure (documented for the team)
```bash
# JS/assets-only fix on the preview channel (runtime must match 1.1.0):
eas update --channel preview --message "Fix Arabic OCR message"

# Promote the EXACT tested update to production (owner-corrected command):
eas update:republish --destination-channel production

# Roll back a bad update (owner-corrected command):
eas update:rollback --channel preview
```
Every publish is announced in-app only after download; nothing about the
user's data or settings changes in an OTA update.

## 9. Implementation phases and realistic blockers

- **Phase 0 — OTA foundation (with the V1.1 APK):** expo-updates + config +
  update screen + channel wiring. *Blocker:* none technical; requires the
  one new APK (§10). Test: publish a JS-only string change to `preview`,
  confirm the 1.1.0 APK picks it up on restart; confirm the 1.0.0 APK
  ignores it (different runtime — actually it lacks the module entirely).
- **Phase 1 — Guardian MVP (foreground):** backend (§4.1 decision) + auth +
  pairing + foreground location sharing + guardian map view + revoke.
  *Blockers:* backend choice; guardian-side client (a second lightweight
  app or the owner-chosen responsive PWA — zero install for
  family members); store-policy-free internal distribution keeps this
  simple.
- **Phase 2 — Background tracking + phone-side hazard alerts:**
  expo-location background task + foreground service, risk engine (§6.3),
  alert delivery, hazard events upload. *Blockers:* Android background
  limits/OEM battery killers (mitigate: foreground service with visible
  notification, battery-whitelisting guidance in-app); background-location
  permission UX (must be requested separately, with the system dialog
  journey explained in Arabic first).
- **Phase 3 — Guardian hazard push + escalation + SOS.** *Blocker:* push
  reliability on OEM devices (FCM via Expo Push is best-effort — stated
  honestly in-app: "alerts are sent immediately but delivery depends on
  the guardian's phone/network").
- **Phase 4 — Glasses integration.** *Blocker:* hardware does not exist.
  Starts only when the hardware team freezes radio/capability specs (§6.6).

Guardian/hazard testing (in addition to §6.5): two-device pairing drills
(code expiry, wrong code, revoke mid-tracking), background survival tests
on 2–3 real Android phones (incl. a Xiaomi/Samsung with aggressive battery
management), offline queue test (airplane mode → reconnect → points
arrive, ordered), and an end-to-end SOS latency measurement. None of this
is claimed done — it is the Phase 1–3 exit checklist.

## 10. Changes that REQUIRE a new APK (native) vs OTA-safe

**New APK required (native/config):**
- Adding `expo-updates` itself (one-time, Phase 0).
- Adding `expo-location`, `expo-task-manager`, `expo-notifications`,
  `expo-secure-store`, maps — any native module.
- New Android permissions (location, background location, foreground
  service, notifications).
- Any Expo SDK / React Native upgrade; any config-plugin change
  (app.json `plugins`, manifest-affecting fields); icon/splash/package
  changes. Each of these also bumps `version` → new runtimeVersion → old
  APKs stop receiving new JS (by design).

**OTA-safe (JS/assets only, same runtime):**
- Screens, navigation, i18n strings, hazard thresholds/taxonomy tuning,
  risk-engine logic, OCR post-processing, TTS wording, bug fixes in TS,
  new sample images, model *post-processing* code. (Replacing a `.tflite`
  model file is an asset change and can ship via OTA **only if** the new
  model keeps the same input/output contract — treat model swaps as
  release-managed events and test on-device regardless.)
