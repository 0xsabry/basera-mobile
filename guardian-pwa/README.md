# BASERA Guardian PWA

The Guardian PWA is a separate, installable web client for a person who has been paired with a BASERA wearer. It is built with static HTML, JavaScript, CSS, a web manifest, a service worker, Supabase JS, Leaflet, and OpenStreetMap tiles.

## Current deployed contract

This README follows docs/SUPABASE_INTEGRATION.md and the deployed backend contract, not the archived local database design.

- Guardians sign in using their own Supabase account.
- A guardian accepts an invite code generated by the wearer.
- Accepting an invite creates an active paired link immediately. The deployed backend has no pending owner-approval stage.
- Location and SOS consent are per link and start disabled.
- The PWA can show only the latest location row available under RLS; there is no deployed 24-hour location history.
- The PWA can show SOS rows only when the deployed per-link SOS consent permits access.
- Browser push is not connected to the deployed backend. The PWA tells the user that server-backed browser notifications are not wired.

Do not use the archived local-design migrations or functions to configure the live backend.

## Files

| File | Purpose |
|---|---|
| index.html | PWA shell and page structure |
| app.js | Supabase sign-in, pairing acceptance, latest-location/SOS queries, map and UI logic |
| config.js | Public Supabase project URL and publishable client key; optional local Firebase web settings |
| manifest.webmanifest | Installability metadata |
| service-worker.js | App-shell caching; it does not turn remote Guardian data into offline history |
| firebase-messaging-sw.js | Experimental/inert FCM browser handler; not backed by the current deployed Supabase push contract |
| freshness.js / realtime.js | Location freshness and live refresh helpers |
| icons/ | PWA icons |

## Configuration and hosting

The checked-in config.js contains public client configuration for the owner's Supabase project. It must never contain a service-role key, database password, FCM server credential, or any other secret.

Serve the folder from an HTTPS static host to enable installation and service-worker behaviour. Before assuming the PWA is publicly deployed, verify the actual hosting URL and the allowed Supabase Auth redirect origin with the owner.

A Firebase browser configuration and VAPID public key alone do not implement server-side notification delivery. The deployed backend currently has no browser push endpoint registration contract.

## Security and privacy

- All remote access uses the signed-in user's JWT and deployed Supabase RLS policies.
- Never weaken RLS to make a screen work.
- Never add a service-role key to config.js or browser JavaScript.
- Do not use real wearer or guardian accounts in a classroom demo; create dedicated test accounts with explicit consent.
- The PWA should display only data returned by the actual authorized backend and must not invent locations or notification delivery.

## Development

This is a static PWA; there is no bundler build step. Open it through a local HTTPS-capable server or localhost during development. See docs/SUPABASE_INTEGRATION.md for the deployed table and consent contract.
